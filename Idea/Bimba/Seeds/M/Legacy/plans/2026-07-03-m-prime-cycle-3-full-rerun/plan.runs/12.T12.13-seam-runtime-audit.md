## A. Embedding-dimension seam — GREEN dimensionally, split by name

**Live proof.** Over the real gateway wire, `s5'.gnostic.status` and `s5'.gnostic.models` both return `embedding_dim: 3072` with `embedding_model: gemini-embedding-2-preview`, `neo4j_uri: bolt://localhost:7687` (capture run B). On the Bimba side, a live `SHOW VECTOR INDEXES` reports `coord_embedding` on `:Bimba(c_5_embedding)` at **3072 / COSINE**. Both halves of the shared space agree at 3072 at runtime.

Three qualifications the ledger must carry rather than smooth over:

1. **It is not one env var.** [[S2]] `graph-services/src/embeddings.rs:27` reads `GEMINI_EMBED_DIMS` (falling back to `GEMINI_EMBEDDING_DIMS`). [[S5]] `epi_gnostic/config.py:33` and `graphiti_config.py:40` read `GNOSTIC_EMBEDDING_DIM`. Neither name appears in the other tree. `GEMINI_EMBED_DIMS=3072` configures Bimba only; it has no effect whatsoever on Gnosis. The Aletheia `CONTRACT.md:163` states the unified value as `GEMINI_EMBED_DIMS=3072`, which is true of the *number* and false of the *mechanism*.
2. **The spec's Verify line is not literally met.** It asks that the dimension grep "return a single value". `config.py:6` declares `VALID_EMBEDDING_DIMS = {128, 256, 384, 512, 768, 1024, 1536, 2048, 3072}` — nine accepted values — and `tests/test_config.py:20-24` proves a `GNOSTIC_EMBEDDING_DIM=768` override is accepted. What is single is the **default** (3072) and the error-message canon (`config.py:52`, "Canonical is 3072."). An env override can therefore stand up a Gnosis store whose dimensionality disagrees with the 3072-dim Bimba vector indexes, and nothing refuses it. Narrowing the valid set is a contract decision; recorded, not patched.
   - This corrects the 2026-07-07 evidence on this row, which claimed the clause was "satisfied (single VALID value)". That claim was false.
   - **Superseded 2026-07-31 by the Architect's ruling** (see §E): `VALID_EMBEDDING_DIMS` is now `{3072}` and `GNOSTIC_EMBEDDING_DIM=768` is *refused*, so as of `52b65f80` the Verify line **is** literally met. Finding 2 stands as the record of why it was not, not as live state.
3. **The pre-existing 3072 assertion is a guard true by construction.** `tests/gate_epii_agent_access.rs:704` sets `GNOSTIC_EMBEDDING_DIM=3072` on a *stub* python harness and then asserts the gateway returns 3072. It proves transport, not the default. The wire capture above is the first proof against the real `epi_gnostic` config.

## B. Cross-namespace edge seam — the seam that was declared and never fired

**Naming verdict: the code is right, the prose is stale.** The spec and the Aletheia `CONTRACT.md` (:146, :262) name `RELATES_TO_COORDINATE`. Nothing creates it. The live name is `MAPS_TO_COORDINATE`, and it is the name in `enrichment/coordinator.py:90`, `tests/test_enrichment.py:205`, `tests/test_cross_namespace.py`, `epi-cli/tests/graph_client.rs:158`, and the `bimba-mcp` relation vocabulary. Correct the prose to the code, not the reverse.

> A prior ledger entry justified this as "the landed name is the one in `graph-schema`". **That is false.** `Body/S/S2/graph-schema/` contains *neither* spelling; the edge type is declared in no schema at all. The reason to prefer `MAPS_TO_COORDINATE` is that it is what executes, not that a schema blesses it.

**The offline acceptance is green.** `pytest tests/test_enrichment.py -v` against live Neo4j (auth-less `bolt://localhost:7687`, `NEO4J_AUTH=none`) = **3 passed**, including `test_cross_namespace_edge_created`.

**But that test calls `CoordinateEnricher` directly. The runtime route to it did not exist.** Three findings, in order of severity:

1. **`GnosisCmd::Enrich` was mis-wired to the ingester.** `epi-cli/src/techne/gnosis/mod.rs` dispatched `Enrich` to `ingest::ingest_gnostic`, spawning `epi-gnostic ingest <entity_id>` — handing an entity id to the document-ingest path as a file path. The `enrich` branch of `epi_gnostic/cli.py:147-170`, the only route to `assign_direct`, was **dispatched by nothing in the repository**. Since the Aletheia Pi tool `aletheia_gnosis_enrich` spawns exactly this command, [[S4]] could not reach the [[S5]] enricher at all.
   **Repaired in this tranche**, red-then-green: `tests/gnosis_commands.rs::gnosis_enrich_dispatches_the_enrich_subcommand_not_ingest` asserts the observed subprocess argv. Red: `["ingest", "gnostic-entity-42", …]`. Green: `["enrich", "gnostic-entity-42", "--coordinate", "M3", "--family", "M"]`.
   **Live end-to-end proof of the repair:** against real Neo4j and the real venv bridge, `epi techne gnosis enrich 't12t13-probe-vid' --coordinate '#0' --family '#'` returned `{"status":"ok","method":"direct","coordinate":"#0"}`, and a read-back showed a real `MAPS_TO_COORDINATE {method:'direct', confidence:1.0}` edge onto `:Bimba {coordinate:'#0'}`. This is the first time the clause-(b) seam has fired through its own route rather than through a test calling the library.
2. **There is no `s5'.gnostic.enrich` gateway method.** The handshake advertises 13 `s5'.gnostic.*` methods (`ingest`, `query`, `resolve`, `musical_transcript`, `notebook`, `status`, `models`, `candidates`, `etymology`, `list_notebooks`, `episode_search`, `evidence_trace`, `query_with_layers`); `enrich` is absent, and calling it returns `unimplemented` in both capture runs. The cross-namespace edge is reachable from the CLI/Pi-tool path but **not from the gateway** — so no [[M']] carrier can mint one. Adding the route is a contract-surface change; flagged, not landed.
3. **The enricher's workspace knob is never supplied on the live path.** `cli.py:113` and `cli.py:153` both construct `CoordinateEnricher(driver, config.neo4j_database)` and omit the third parameter, so the workspace label is hardwired to the default `"gnostic"` while `wrapper.py:85` writes storage nodes under `config.workspace` (`GNOSTIC_WORKSPACE`). With a non-default workspace the enricher's `MATCH` finds nothing and the `MERGE` never runs — **a silent no-op, no error**. Recorded; the fix is a one-argument change but it alters enrichment scoping semantics, so it belongs to the owning spec.

**Live graph safety.** Read-only throughout except the scoped probe above, which used a private `:t12t13probe` label plus a unique `vector_id` and was removed by a doubly-scoped `DETACH DELETE`. Integrity held exactly: 3296 nodes / 13344 relationships / 2141 `:Bimba` before **and** after, with 0 residue.

## D. Additional runtime findings

1. **The default gnostic bridge binary is broken.** `GnosisConfig` defaults `python_bin` to `epi-gnostic` from `PATH` (`techne/gnosis/config.rs:26`). The `PATH` entry at `~/Library/Python/3.13/bin/epi-gnostic` raises `ModuleNotFoundError: No module named 'epi_gnostic'`. Capture run A (no `EPI_GNOSTIC_PYTHON`) shows **every** `s5'.gnostic.*` method failing with that traceback over the wire. Under default environment the entire S4↔S5 gnostic seam is dark; it works only when `EPI_GNOSTIC_PYTHON` is pinned to the venv console script. This is environment/packaging state, recorded here because it is the runtime truth of the seam and no test covers it.
2. **The gateway does not propagate graph credentials to the S5 bridge.** With the bridge correctly pinned, `s5'.gnostic.query` still fails: LightRAG's `Neo4JStorage` demands `NEO4J_URI`, `NEO4J_USERNAME`, `NEO4J_PASSWORD`, and the gateway passes none. `.env.graph-dev` exports the same values under `EPILOGOS_NEO4J_*`. A third naming split on the same seam, and the reason gnosis-RAG *retrieval* does not run at runtime.
3. **Two declared tool parameters are silently dropped.** `aletheia_gnosis_query` declares `notebook` and `top_k`; `execute` reads neither, and `GnosisCmd::QueryGnostic` has no flags to receive them. An agent that sets either gets no error and no effect. Wiring them requires new flags across three layers — interface widening, flagged rather than landed.
