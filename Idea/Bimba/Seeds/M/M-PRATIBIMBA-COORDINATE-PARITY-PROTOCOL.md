# M / M′ Bimba-Pratibimba Coordinate Parity Protocol

## 0. Why this protocol exists

The Bimba map is not background documentation from which an implementation may freely extract a convenient feature list. It is the authored relational specification of the Epi-Logos M field. The M′ instruments are the functional / technological reflection of that field.

That relation creates a development obligation:

> **An M′ implementation must remain answerable to the actual coordinate and relation structure of its M Bimba source.**

This does **not** mean every Bimba coordinate must already have a complete software capability or visible UI. It means that absence of implementation must not erase coordinate identity, change parentage, flatten recursion, invent a replacement ontology, or make a later instrument unable to discover where it belongs.

The practical failure this law prevents is subtle. A developer can correctly build a useful Nara journal and still accidentally build the wrong Nara architecture if the journal becomes the local root of a new data model. The authored system says something more specific: lived activity belongs under M4-4′, converges at the recursive #4.4.4.4 Personal Pratibimba carrier, supplies evidence to M4-5′ review, and may affect M4-0′ identity only through governed return. A feature-only implementation can preserve the nouns "Nara", "journal", and "Epii" while losing that relation.

The same risk applies to every M′ subsystem. This protocol makes the relation testable before more instruments harden around partial local models.

---

## 1. The four things that must not be collapsed

### 1.1 Bimba coordinate truth

The accepted M map says that a coordinate exists, where it sits, which coordinate contains it, and which relations are constitutive of it.

Examples:

- M4 contains the six M4-0 … M4-5 branches;
- M4-4 contains its own sixfold differentiation;
- #4.4.4.4 is recursive deepening of the #4 path, not a seventh top-level Nara module;
- M4-5 returns toward M4-0 only under the review/promotion law.

Coordinate truth is not invalidated because no current provider implements the coordinate.

### 1.2 M′ reflection identity

Every accepted M coordinate which participates in an M′ instrument must have a stable reflected identity preserving the exact coordinate path.

Conceptually:

```text
M4-4-4-4       Bimba coordinate
    │
    │ conjugate reflection
    ▼
M4-4-4-4′      Pratibimba coordinate
```

The prime does not mean "a related feature we happened to build". It means the functional reflection of the same differentiated position.

### 1.3 Implementation state

A reflected coordinate may currently be:

```text
implemented
partial
unbound
research
not-assessed
provider-unavailable
```

Those are facts about current software, not facts about whether the coordinate exists.

The implementation state is allowed to change while coordinate identity remains stable.

### 1.4 Experienced surface

A coordinate being first-class in the executable model does not require it to become a card, tab, dashboard, route, or visible control.

Nara remains the clearest example. The default M4′ experience should be quiet lived writing and present context. The sixfold internal structure is load-bearing beneath that surface precisely so the user does not need to operate the architecture manually.

## 2. Five parity levels

"Parity" must not be used as one undifferentiated claim.

### P0 — Source parity

The implementation programme can identify the accepted Bimba source corpus, its revision/provenance, and the coordinates/relations currently treated as authoritative.

If the source corpus contains unresolved or conflicting strata, the manifest records that uncertainty. It does not silently choose whichever interpretation makes coding easiest.

### P1 — Coordinate parity

Every accepted coordinate in scope has an executable, stable coordinate Ref preserving:

- M root;
- full granular path;
- Bimba / Pratibimba face;
- parent coordinate;
- source coordinate notation/ref;
- semantic name where authored;
- source provenance.

A missing capability is represented as a state on the coordinate, not by deleting the coordinate.

### P2 — Relation parity

Constitutive Bimba relations in scope are represented as typed executable relations between stable coordinate Refs.

At minimum the substrate must be capable of preserving:

- containment / parent-child relation;
- exact-path Bimba ↔ Pratibimba conjugate reflection;
- cross-coordinate routing;
- evidence flow;
- governed return/promotion;
- cross-M relations where the source map makes them constitutive;
- deeper relation classes as the accepted Bimba relation vocabulary is recovered.

A generic graph edge is not sufficient if the source distinguishes kinds of relation that matter operationally.

### P3 — Operational parity

A software capability actually enacts the relation it claims.

Examples:

- a M4-4′ journal episode carries the M4-4′ coordinate and is anchored at the Personal Pratibimba carrier;
- a M4-5′ review Action consumes evidence rather than mutating M4-0′ directly;
- an M3′ transcription service does not merely label itself M3 while bypassing the M3 coordinate relations it claims to realise.

Operational parity is stronger than coordinate parity and must be evidenced separately.

### P4 — Experiential parity

The human/agent instrument presents the right lived affordance for the coordinate relations without forcing the internal map into the foreground.

Experiential parity is therefore not "display all coordinates". It asks whether the architecture has the right consequence for use.

## 3. Core executable law

Every M′ subsystem development must consume one shared Epi-owned coordinate substrate rather than defining its own local coordinate enum or feature ontology.

The core substrate must support:

```text
MCoordinate
  root
  granular path
  face = bimba | pratibimba
  stable canonical Ref
  parent

MCoordinateNode
  source Ref
  semantic name
  reflected Ref
  implementation/readiness state
  provenance

MCoordinateRelation
  typed relation
  from Ref
  to Ref
  source basis
  status/provenance
```

The important property is that the shape exists before any particular UI, provider, or agent workflow decides how much of it to realise.

No M′ application is allowed to create a second incompatible coordinate identity because it wants a simpler local state model.

---

## 4. Coordinate-reflection law

For every reflected coordinate:

```text
path(Mx.y.z) == path(Mx.y.z′)
root(Mx.y.z) == root(Mx.y.z′)
face(Mx.y.z) != face(Mx.y.z′)
```

Reflection changes face, not structural identity.

A provider may attach capability/readiness data to the M′ face. It may not relocate the capability to another coordinate merely because the implementation is easier there.

Where historical code uses older naming, compatibility aliases may be retained, but the alias must resolve to the canonical coordinate rather than becoming another semantic object.

---

## 5. Recursive-coordinate law

Hierarchical data structures may technically nest anywhere, but authored QL/Bimba recursion must retain its specific meaning.

In Nara, #4.4.4.4 is the critical example:

```text
M4
 └─ M4-4
     └─ M4-4-4
         └─ M4-4-4-4
```

This is not equivalent to adding an arbitrary seventh sibling under M4.

Executable coordinate identity must therefore preserve the entire path, not only the nearest feature category.

Future M′ subsystems must apply the same rule wherever the Bimba map contains meaningful recursive depth.

---

## 6. Relation law

Coordinates alone are insufficient. The Bimba map specifies a relational shape.

The executable reflection must therefore retain relation identity independently of whatever service currently traverses it.

For Nara the first non-negotiable relation chain is:

```text
M4-4′ lived/context field
        │ anchors-at
        ▼
M4-4-4-4′ Personal Pratibimba
        │ supplies-evidence-to
        ▼
M4-5′ review / Epii integration
        │ governed-return-to
        ▼
M4-0′ identity/quintessence
```

This is why a journal-derived observation cannot become an identity write merely because both structures happen to be available in one process.

As the full Bimba relation corpus is recovered into a machine-readable source, the same rule expands: accepted source relations become typed executable relations or explicit unresolved gaps. They are not discarded because a current vertical does not use them yet.

---

## 7. Instrument-rooting law

Every M′ instrument, Surface, Action, episode, artifact, provider, and agent handoff that makes a semantic M claim must identify its coordinate lineage.

Depending on the object, this may include:

- origin coordinate;
- current instrument coordinate;
- recursive carrier coordinate;
- review/return coordinate;
- related cross-M coordinates;
- source-manifest Ref;
- source revision.

This makes it possible for a human, agent, test, or later migration to ask not merely "what feature produced this?" but "where in the authored relational system does this object live?"

The smallest sufficient lineage should travel with the object. Do not dump the whole Bimba map into every context packet.

## 8. Development protocol for every M′ subsystem

Before substantial feature work begins on Mx′:

```text
accepted Bimba/M source corpus
        ↓
coordinate inventory
        ↓
relation inventory
        ↓
executable coordinate/relation manifest
        ↓
manifest parity tests
        ↓
current native substrate mapped onto coordinates
        ↓
first bounded M′ capability
        ↓
objects/events carry exact coordinate lineage
        ↓
instrument / Surface
        ↓
operational + experiential acceptance
```

A Factory agent must not skip from "read the Mx′ spec" directly to "implement feature list".

The coordinate/relation inventory is not optional architecture ceremony. It is the mechanism that prevents a partial vertical from becoming a replacement ontology for the whole subsystem.

---

## 9. Required acceptance tests

Every M′ development line must eventually prove the following for its accepted source scope.

### Coordinate coverage

- every accepted in-scope Bimba coordinate resolves;
- no executable M′ coordinate lacks a Bimba/source basis unless explicitly marked experimental;
- exact coordinate path survives reflection;
- parent coordinates exist;
- required sixfold children are complete where the source declares a sixfold;
- recursive coordinates preserve their full path.

### Relation coverage

- every accepted constitutive source relation in scope has a typed executable counterpart or explicit gap record;
- generated containment edges agree with coordinate parentage;
- every M/M′ pair has an exact conjugate-reflection relation;
- governed-return edges cannot be replaced by direct mutation paths.

### Implementation honesty

- structural coordinate existence is not reported as implemented capability;
- a provider's availability does not imply coordinate authority;
- a UI label does not count as operational parity;
- historical code similarity does not count as parity without source mapping.

### Provenance

- coordinate and relation manifests identify their source corpus;
- returned objects identify manifest/ref revision sufficiently for audit;
- stale source-manifest assumptions are detectable.

## 10. Nara as the proving case

The first implementation of this protocol is intentionally smaller than a claim of complete Nara capability.

The current executable floor contains:

- M4 root;
- all six M4-0 … M4-5 coordinates;
- the complete first internal sixfold under each of those six branches;
- the recursive #4.4.4.4 Personal Pratibimba carrier;
- exact Bimba ↔ Pratibimba reflection for every represented coordinate;
- containment relations;
- the lived `M4-4′ -> M4-4-4-4′ -> M4-5′ -> M4-0′` evidence/review/return chain.

The Prompt-B daily episode is now rooted at M4-4′ and carries #4.4.4.4 as its protected living carrier. The existing root world address remains as compatibility/context; it no longer has to bear the entire semantic burden of saying where the daily artifact actually lives.

This is a **structural floor**, not a claim of complete 100-node historical Nara map parity. Current Nara source prose refers to a 100-node / 284-relation deep dataset at a path that is not present in the current repository location. Until that source is recovered or canonically superseded, the implementation must not fabricate the missing deep node/relation corpus. The gap is explicit and should be closed as source-reconstitution work, after which the manifest coverage test becomes count/content exact against the accepted machine source.

That distinction is itself part of the protocol: truthfully partial coordinate parity is preferable to a falsely complete map.

## 11. Generalisation across M0′–M5′

Nara is not special in needing this law; it is simply the first lived vertical that exposed the omission clearly.

For each subsequent subsystem:

```text
M0 ↔ M0′
M1 ↔ M1′
M2 ↔ M2′
M3 ↔ M3′
M4 ↔ M4′
M5 ↔ M5′
```

we should build from the same core coordinate/relation substrate.

The domain-specific manifests differ; the coordinate grammar and parity rules do not.

This allows later integrated instruments — Personal 4/5/0, Cosmic 1/2/3, and deeper six-instrument compositions — to compose already-rooted coordinate systems rather than reverse-engineering semantic ownership from feature code.

---

## 12. Ownership boundary

Epi owns the M/Bimba domain map and its M′ reflection semantics.

QL-MEF may supply general formal coordinate, lens, relation, conjugacy, and refraction machinery where those operations have become genuinely general. O:I may host the resulting Surfaces/Refs. AIKit/Actuation may disclose or actuate capabilities against them. None of those products becomes the semantic owner of the Epi M map merely by providing generic infrastructure.

Likewise, Neo4j or any future Bimba store is a material source/provider body, not the meaning of Bimba itself.

---

## 13. Factory-agent rule

A development agent working on an M′ subsystem should be able to state, before significant implementation:

1. which Bimba coordinates and relations are in scope;
2. which canonical manifest represents them;
3. which coordinates have existing native substrate;
4. which are unbound or research-only;
5. where the vertical is rooted;
6. which return/review relation governs mutation;
7. which parity tests will fail if it accidentally flattens the map.

If it cannot answer those questions, it does not yet have enough architectural ground to redesign the subsystem.

The goal is not bureaucratic fidelity to a diagram. The goal is that software remains a true enough Pratibimba that development can deepen the system without first reconstructing the Bimba relation that the previous implementation erased.
