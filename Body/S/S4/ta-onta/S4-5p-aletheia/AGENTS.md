Config never enters this module — it arrives as an `AletheiaEloConfig` parameter. `resonance72-retrieval.ts` (12.T12.13 clause c) is the consumer the 72-fold address never had: `MathemeHarmonicProfile.resonance72` is derived kernel-side and emitted by [[Anima]]'s VAK emitter, but BOTH gnosis-RAG entry points — the `aletheia_gnosis_query` tool and this carrier's own `spine-contribution.ts` query handler — spawned `query-gnostic <question> --mode hybrid` with no channel for a harmonic address, so the value never crossed the seam. It reads the live projection off `epi profile show` and folds it into the question, following the `[coordinate context: X]` idiom already in the tool (retrieval is hybrid over natural-language chunks, so a conditioning term must reach the embedding to affect ranking; a side-channel parameter the retriever never reads would be decoration). It REFUSES rather than invents — unreadable, out-of-domain, or self-inconsistent-with-its-own-components yields `null` and the question goes out unconditioned, the same discipline `vak-eval-emit.ts` applies to `mef_lens`. Both entry points are wired; conditioning only one would leave half the seam dark. **Declared tool parameters must reach the substrate or not be declared (12.T12.13 finding D3).** `aletheia_gnosis_query` shipped `notebook` and `top_k` that `execute` never read: `top_k` is now plumbed through to LightRAG's `QueryParam`. `notebook` was first REMOVED on the false premise that notebooks are "a registry, not a retrieval partition" — **that was wrong and is corrected (2026-08-01)**. Notebooks are runtime SOURCE POOLS, session-rooted, operated via psyche -> [[Nous]]: `nous_disclose` creates `khora-session-<session_id>` and ingests the curated context package into it with `--source-type SessionContext`, and `query_local` filters retrieval by notebook (`SourceSelection.notebook`, `GnosisQueryHit.notebook`). Retrieval over a notebook is THE thing session pools exist for. **The real distinction is two stores, not two kinds of thing:** notebook scoping is implemented in the LOCAL gnosis store (`techne/gnosis/{ingest,query}.rs`, `documents.json`/`notebooks.json`) and is NOT wired through the LightRAG/Neo4j path that `query-gnostic` uses. So `aletheia_gnosis_query` routes by parameter — `notebook` set goes to `epi techne gnosis query --notebook`, which actually partitions; unset goes to `query-gnostic` hybrid RAG. Proven: ingest into `khora-session-probe1` then query scoped to it HITS, and the same query scoped to another notebook returns `no matches`. `aletheia_gnosis_ingest`'s `notebook` was worse than dropped: it pushed `--notebook` at a CLI arm that did not accept the flag, so clap refused the invocation and the ingest FAILED outright whenever an agent set it; the arm accepts it now and records the document against the registry. Making notebook-scoped RETRIEVAL real needs chunk-level tagging plus a retrieval filter, and is unbuilt.
