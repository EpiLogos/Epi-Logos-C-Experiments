# S0' — Kernel Inverse — Hermes Alignment
Date: 2026-06-07

## Adopt (Hermes → Epi-Logos)

1. **Check_fn availability gating (hermes registry.py → epi-kernel-contract ingestion.rs)**
   Hermes's `tools/registry.py::ToolEntry` carries a `check_fn: Callable[[], bool]` that gates whether a tool is available in the current session — checking env vars (`requires_env`), installed dependencies, authentication state. When `check_fn()` returns `False`, the tool schema is omitted from the LLM's tool list entirely. Epi-Logos's `epi-kernel-contract/src/ingestion.rs::IngestionSession` has protocol-order enforcement (`record_envelope` rejects out-of-order or element-mismatched envelopes) but no availability gating — if a required subsystem (Neo4j, Redis, epi-lib FFI) is unavailable, the session fails at invocation time rather than omitting the unsupported operations upfront. Adopting a `check_fn` pattern in `IngestionSession::new()` — e.g., `fn check_requirements() -> Result<(), Vec<String>>` that returns a list of unmet requirements — would let callers surface "Neo4j unreachable, Redis unreachable" before attempting ingestion, matching Hermes's fail-early pattern.

2. **Schema validation at registration time (hermes JSON Schema → epi-kernel-contract constraint.rs)**
   Hermes tool schemas are validated at registration time: `registry.register()` stores a JSON Schema dict, and `model_tools.py` validates tool call arguments against the schema before dispatching. Epi-Logos's `epi-kernel-contract/src/constraint.rs::ConstraintRegistryEntry` carries a Cypher query + Anuttara template but has no schema validation at registration time — constraint correctness is only verified at test time (unit tests in `constraint.rs` parse templates against known bindings). Adding a `ConstraintRegistryEntry::validate()` method that parses the Anuttara template against a set of expected binding keys, plus validates the Cypher query against a grammar (even just syntax-checking), would catch malformed constraints earlier — matching Hermes's registration-time validation pattern.

3. **Requires_env dependency declaration (hermes registry.py → epi-kernel-contract deposit.rs)**
   Hermes tools declare `requires_env: List[str]` — a list of environment variables the tool needs. Epi-Logos's `epi-kernel-contract/src/deposit.rs::TrajectoryDeposit` and `envelope.rs::KernelTickEnvelope` have no explicit dependency declarations. A `TrajectoryDeposit` requires Neo4j (for persistence), Redis (for context caching), and the epi-lib C engine (for bioquaternion computation) — but none of these are declared. Adding `requires_subsystem: Vec<String>` (e.g., `["neo4j", "redis", "epi-lib"]`) to the deposit/envelope constructors would let the ingestion session check subsystem availability upfront, matching Hermes's pattern.

4. **Runtime availability re-check pattern (hermes registry.py is_available → epi-kernel-contract analysis.rs)**
   Hermes's registry supports dynamic re-checking: `check_fn` can return different results as the environment changes (e.g., API key added mid-session). Epi-Logos's `epi-kernel-contract/src/analysis.rs::ResonanceAnalysis` computes `DominantPosition` and `PrehensiveExtractions` from a `ResonanceVector72` but has no dynamic availability check — if the resonance vector hasn't been populated (observed_resonance is `None`), the analysis silently returns defaults. Adopting an `is_available()` check that returns `false` when prerequisite data is missing would make the contract more honest about its runtime readiness.

## Enrich (Epi-Logos → Hermes)

1. **Constraint registry with Cypher queries and Anuttara templates (epi-kernel-contract constraint.rs → hermes tool check_fn)**
   Epi-Logos's `ConstraintRegistryEntry` is significantly richer than Hermes's `check_fn`. A constraint entry carries: a named Cypher query (graph-structured verification), a severity level (`Info`/`Warning`/`Error` — progressive promotion model), an Anuttara symbolic template with `{key}` substitutions, an `enabled` flag, and a `render()` method that produces an `AnuttaraDiagnostic` from query result bindings. The `VerifierReport` aggregates violations with `max_severity()` and `synthesise_diagnostic()`. Hermes's `check_fn` returns a bare `bool` — no diagnostic, no severity, no symbolic explanation. Hermes could adopt a `ToolDiagnostic` type: check_fn returns `Result<(), Vec<ToolDiagnostic>>` where each diagnostic has a severity, a human-readable message, and an optional fix suggestion. This would make tool availability failures operator-actionable instead of silently dropping tools.

2. **Anuttara symbolic verification notation (epi-kernel-contract diagnostic.rs → hermes tool validation output)**
   Epi-Logos's `AnuttaraDiagnostic` grammar (402-line parser in `diagnostic.rs`) supports: `○` (coherence/silence), `?{inner}` (question marker), `coord{pos-list}` (position emphasis), `coord → coord` (descent relation), `coord ⟷ coord` (mirror pair), `coord ≠ ⟦vector⟧` (resonance discrepancy), `coord'` (helix prime), and compound expressions separated by `;`. This is a deterministic, parseable verification language — no LLM judgement intervenes. Hermes has no equivalent symbolic verification output. While Hermes doesn't need the full coordinate grammar, the pattern of a deterministic, parseable verification notation could enrich Hermes's tool validation: instead of generic "Tool X is unavailable", output a structured `ToolStatus` enum with machine-parseable variants (`MissingEnvVar("API_KEY")`, `OAuthExpired("nous")`, `DependencyMissing("faster-whisper")`) that consumers (gateway, IDE, cron) can act on programmatically.

3. **Progressive promotion model (epi-kernel-contract IngestionSession → hermes tool lifecycle)**
   Epi-Logos's `IngestionSession` traverses the 8-element matheme protocol: Opened → PrehensiveAnalysis → PersistedAnalysis → SlashFlipped → InverseRecognition → DepositedReturn. Each step records a `KernelTickEnvelope` whose element must match the next status — protocol-order enforcement is structural, not advisory. Hermes's tool lifecycle is binary: tool is available or not. There is no progressive readiness model where a tool transitions through states (`registered → configured → authenticated → available`). Adopting a `ToolReadiness` enum with progressive states would make Hermes's tool lifecycle auditable and match the ingestion session's protocol-order pattern.

4. **Compile-time invariant enforcement (epi-lib C headers → hermes toolsets.py)**
   Epi-Logos's C headers (`ontology.h`, `m1.h`, `kernel.h`) use `_Static_assert` extensively — 5 assertions in `ontology.h` alone enforcing struct sizes and field offsets (128 bytes exactly, tensor anchor at byte 8, intra-openness at byte 16, execution zone at byte 112, payload at byte 120), plus percentile invariants (`64 + 36 == 100`), matrix size invariants (`sizeof(DR_Matrix_12x12) == 72`), and quintessence matrix size (`sizeof(Quintessence_Matrix) == 144`). Hermes's `toolsets.py` uses a Python dict with no compile-time or load-time structural checks — if a toolset references a non-existent tool name, it's a runtime KeyError. Hermes could adopt load-time assertions in `TOOLSETS` validation: verify every tool name in every toolset maps to a registered tool, verify every registered tool's toolset exists, and fail at import time with a clear error.

5. **Trajectory deposit with ordered elements (epi-kernel-contract deposit.rs → hermes session logging)**
   Epi-Logos's `TrajectoryDeposit` enforces ordered 8-element trajectories: `push_element` rejects out-of-order `KernelElement` values (must match protocol sequence), `close` finalizes with `ended_at_ms` and `r_energy_total`, and the deposit is immutable after close. Hermes's session transcripts (`~/.hermes/sessions/*.jsonl`) are append-only JSONL with no structural ordering enforcement — any message can follow any message. While Hermes doesn't need the matheme element ordering, the pattern of a `close()` method that finalizes a record and prevents further mutation is valuable: it would prevent corrupted transcripts where a session is left in a dangling state.

## Tighten (specific improvements)

1. **S0' epi-kernel-contract: Add ConstraintRegistryEntry::validate()**
   Current state: `ConstraintRegistryEntry::new()` validates that name, query, and template are non-empty strings, but does not validate the Anuttara template against expected binding keys or the Cypher query against a grammar.
   Proposed change: Add `ConstraintRegistryEntry::validate() -> Result<(), Vec<String>>` that (a) parses the Anuttara template, (b) identifies all `{key}` placeholders, (c) validates each key against a known set, (d) syntax-checks the Cypher query (at minimum, verifies it starts with a valid Cypher keyword like `MATCH`/`CREATE`/`MERGE`). Call `validate()` in the constructor so malformed constraints are rejected at registration time.
   Rationale: Matches Hermes's registration-time validation pattern. Prevents silent failures where a constraint with a typo'd template key (`{coord}` vs `{coordinate}`) produces broken Anuttara output at runtime.

2. **S0' epi-kernel-contract: Add TrajectoryDeposit::is_available()**
   Current state: `TrajectoryDeposit::new()` validates session_key, anchor_coordinate, and canonical_coordinate are non-empty, but doesn't check subsystem availability. If Neo4j is unreachable, the deposit succeeds as a Rust struct but fails when persisted.
   Proposed change: Add `TrajectoryDeposit::check_requirements() -> Result<(), Vec<SubsystemRequirement>>` where `SubsystemRequirement` has `name: String`, `status: RequirementStatus` (`Met`/`Unmet`/`Unknown`), and `message: String`. Check Neo4j connectivity, Redis connectivity, and epi-lib FFI symbol availability. Return unmet requirements so callers can surface them before attempting persistence.
   Rationale: Adopts Hermes's `check_fn` + `requires_env` pattern. Prevents the "runtime error during persistence" failure mode.

3. **S0' epi-kernel-contract: Add VerifierReport serialization to Anuttara format**
   Current state: `VerifierReport` serializes to JSON (serde). The `synthesise_diagnostic()` method produces an `AnuttaraDiagnostic` but there's no CLI command to run verification and emit the report.
   Proposed change: Add `VerifierReport::emit_anuttara() -> String` that renders the full report in Anuttara symbolic notation: one line per violation (e.g., `?#2-1-3-4{2,4}`), followed by `○` if coherent. Add CLI surface: `epi core verify --trajectory <id> --format anuttara|json`.
   Rationale: Makes the verifier ring operator-visible. The Anuttara notation is designed for human consumption — emitting it as a first-class output format closes the loop between constraint definitions and operator feedback.

4. **S0' portal-core: Add compile-time invariant checks for MathemeHarmonicProfile**
   Current state: `portal-core/src/kernel.rs::MathemeHarmonicProfile` has 42 fields (including 7 nested projection structs) with no compile-time size or offset checks. The C headers (`ontology.h`) use `_Static_assert` extensively, but the Rust side has no equivalent.
   Proposed change: Add `const _: () = assert!(size_of::<MathemeHarmonicProfile>() <= SOME_REASONABLE_BOUND);` and `#[test] fn harmonic_profile_field_count_is_stable() { ... }` with an assertion on the number of fields. This prevents accidental field additions from silently bloating the profile.
   Rationale: Adopts the compile-time invariant pattern from the C headers into the Rust crate that defines the canonical profile shape. Ensures the kernel contract's type shapes stay within expected bounds.

5. **S0' epi-kernel-contract: Add IngestionSession::check_readiness()**
   Current state: `IngestionSession::new()` validates inputs but doesn't check if the 8-element protocol can actually be executed (Neo4j for persistence, Redis for context, engine for computation). The session fails partway through when a step can't be executed.
   Proposed change: Add `IngestionSession::check_readiness() -> ReadinessReport` where `ReadinessReport` lists each required subsystem and its status. Return early with a clear error if any subsystem is unavailable, before the session enters the protocol.
   Rationale: Adopts Hermes's fail-early pattern. The 8-element matheme protocol is expensive to abort mid-way — catching subsystem unavailability before BimbaEncoding (element 0) saves wasted computation through elements 1–7.

## Gap (missing on either side)

1. **Gap: Hermes has no verifier ring / constraint registry equivalent**
   Hermes's tool validation is binary availability (check_fn returns bool) with no progressive constraint system. There is no equivalent of Epi-Logos's `ConstraintRegistryEntry` (named Cypher query + Anuttara diagnostic + severity), `VerifierReport` (aggregates violations + coherence recognition), or `IngestionSession` (8-element protocol-order enforcement). This is a significant architectural gap — but Hermes's domain (general-purpose LLM agent tool orchestration) doesn't require structural graph verification. Not a gap to close for Hermes; noted as Epi-Logos's distinctive S0' contribution.

2. **Gap: Epi-Logos has no runtime schema validation of tool arguments**
   Hermes validates LLM function-call arguments against JSON Schema at dispatch time (`model_tools.py`). Epi-Logos's kernel contract types use Rust's type system for compile-time validation (struct field types, enum variants) but have no runtime schema validation layer — if a gateway message arrives with malformed JSON, serde deserialization fails with a generic error. Adding a `Validate` trait to `epi-kernel-contract` types that produces structured validation errors (field name, expected type, received value) would close this gap. Medium priority — the serde error messages are adequate for development but insufficient for gateway-facing error reporting.

3. **Gap: Hermes has no deposit/anchor model for session persistence**
   Hermes sessions are append-only JSONL with no structural closure — there is no equivalent of `TrajectoryDeposit::close()` that finalizes a record and prevents further mutation. A Hermes session can be resumed indefinitely with no "this session is complete" marker. This is by design (Hermes sessions are conversational, not protocol-bound) but means there's no way to programmatically know when a session is done. Low priority — the `TrajectoryDeposit` model doesn't fit Hermes's conversational paradigm.

4. **Gap: Epi-Logos's Anuttara verifier has no runtime integration**
   The `AnuttaraDiagnostic` parser (402 lines), `ConstraintRegistryEntry` renderer, and `VerifierReport` aggregator are fully implemented and tested — but there is no runtime pipeline that runs Cypher constraints against Neo4j, feeds bindings into the template renderer, and emits `VerifierReport`. The types exist but the execution loop doesn't. High priority — this is the most significant gap in the S0' layer. The contract shapes are ready; the verifier runtime needs to be built.

5. **Gap: Hermes has no symbolic notation for tool validation output**
   Hermes tool validation produces boolean results and log messages. There is no structured, machine-parseable diagnostic notation equivalent to Epi-Logos's Anuttara grammar. This makes it impossible for external systems (monitoring, CI, gateway platforms) to programmatically understand WHY a tool is unavailable. Medium priority — a `ToolDiagnostic` type with structured variants would unlock automated recovery (e.g., "OAuth token expired for provider X → trigger re-auth flow").

## Verdict

S0' alignment reveals a **strong asymmetry in verification depth**: Epi-Logos has a rich contract-verification architecture (constraint registry, Anuttara diagnostic grammar, progressive ingestion protocol, compile-time invariants) with fully implemented types and tests — but no runtime execution pipeline. Hermes has a simple but effective runtime validation pattern (check_fn + schema validation + requires_env) that gates tool availability at every turn — but no diagnostic depth, no progressive promotion, and no symbolic output. The most valuable adoptions are bidirectional: Epi-Logos should adopt Hermes's `check_fn` / `requires_env` pattern as `check_requirements()` methods on `IngestionSession`, `TrajectoryDeposit`, and `ConstraintRegistryEntry` to achieve fail-early behavior; Hermes should adopt Epi-Logos's structured diagnostic types (`ToolDiagnostic` with severity + symbolic message) to make tool availability failures machine-actionable. The highest-priority gap is the missing Anuttara verifier runtime pipeline — the constraint registry, diagnostic parser, and verifier report types are implementation-ready but need an execution loop that runs Cypher constraints against Neo4j and materializes `VerifierReport` instances. Recommended next step: implement `epi core verify` as a CLI command that executes the constraint pipeline end-to-end, and add `check_requirements()` to all kernel-contract entry points.
